## 根拠の区分

- S（静的確認）: 指定SHAのコード本文で確認した内容。
- U（ユーザー報告）: ユーザーが実機で確認した結果。AIが実行したものではない。
- H（履歴・旧資料）: 過去の記録。現在の実装確認と同一視しない。
- Q（未確認）: 本文未読、応答省略、未試験などで断定できない内容。
- P（提案）: 将来案。ユーザー承認・実装済みとは扱わない。

基準SHAはコード調査の固定版。ユーザーはローカルpush済みと報告しているが、実行ログにコミットSHAは埋め込まれていない。

## 3. 現在地

- ローカルはpush済みとユーザーが報告。
- WinMainがSystem寿命・フレームを管理し、SceneManagerがCurrent / Next / Progress / Fadeを管理。
- Nextを要求時に生成し、黒画面時にInitialize / Init。成功後に旧Sceneを終了。
- Fade双方でScene Update停止、描画とSystem更新は継続。
- ShopはUpdate / Draw分割、Gate分離、Raycast利用、Table、購入結果enumまで確認。
- 過去提案のShopInteractionHit / FindNearestInteractionHitは現Shopに未反映。
- GameはLow HP呼出1回、progress.Update、Tutorial設定、Gate / F2要求化を確認。
- Enemy Draw二重呼出が残り、死亡は直接Shop予約経路。
- WM_SIZE接続、Game / Shopの動的Aspect確認。Canvasファイルは存在、全適用未監査。
- 全System内部・Shader契約・Asset基盤の監査は未完了。

## コード出力の共通基準

正式な詳細規約は「GunfireLike 統合コーディング規約・命名規則・コード出力前レビュー」版1.1（2026-11-05）を共有して参照する。
以下は取り違え防止の要約であり、統合規約を置き換えない。

- スペース2個、タブ禁止。インデント・引数整列を含めて180文字以内。
- 長い引数は意味グループで分け、継続行を最初の引数位置へそろえる。
- 同じ目的の処理はまとめ、異なる責務の間は空行1行。
- include順: 対応Header（cppのみ）→Windows→C++標準→外部ライブラリ→Debug→Framework→Scene。
- クラス・メソッド・型エイリアス・ファイル名: UpperCamelCase。
- struct / enum型名: UPPER_SNAKE_CASE。列挙子: e_UPPER_SNAKE_CASE。
- クラス通常メンバー: m_lowerCamelCase。構造体フィールド・通常引数: lowerCamelCase。
- ローカル: snake_case。略語HP / UI / GPU / FPSなどは大文字を維持。
- namespace名: UPPER_SNAKE_CASE（ns_を付けない）。namespace内の定数: ns_UPPER_SNAKE_CASE。
- クラスの定数メンバー: m_UPPER_SNAKE_CASE。
- 型テンプレート仮引数: TValue形式。数値等: ELEMENT_COUNT形式。
- Header先頭、グループ、メソッド、各引数、メンバー、enum / structと各要素へ説明を書く。
- Header宣言順とcpp定義順を対応させ、出力前にチェックシートで確認する。
- 未変更の既存API名や外部APIを勝手に改名しない。一括改名は別タスク。

## 4. スペースごとの責務

| 担当 | 行うこと | 行わないこと |
|---|---|---|
| ユーザー | 目的・優先の判断、資料受渡、コード適用、Build / 実機検証、採否 | AIの未検証主張を実測扱いしない |
| 設計・プロンプト | 完成図、責務・依存・所有、タスク分割、受入条件、実装依頼作成 | 未確認APIを実在として指定、勝手な一括改修 |
| 実装（既存会話） | コード読解、前提照合、最小差分、規約チェック、検証結果レビュー | 不整合な依頼を黙って別設計へ変える |

## 5. 禁止事項・注意事項

- コードの取得成功だけで本文読了としない。省略された応答は未読部分を明示する。
- 過去の動作確認を最新の全機能保証へ広げない。
- 旧タスクIDを単独で使わない。Shop C-06とFramework C-06を混同しない。
- 過去のC-07案を承認済みの必須工程へ昇格させない。
- 現行識別子を新命名へ脳内変換して存在するAPIとして依頼しない。
- 未改名の既存APIは正確な現名を記載し、新規名・移行後名と分ける。
- 全体リファクタリングより、目的と受入条件のある最小単位を選ぶ。
- 実施していない会議の議事録や合意・ビルド結果を作らない。

## 6. 初回の応答で行うこと

1. 基準版・確認範囲・未確認を短く要約する。
2. 完成図で決める事項を旧目標から抽出し、必須 / 発展 / 非対象の案へ分ける。
3. まだ必要な質問を少数に絞る（完成期限、対象ゲーム、必要機能等）。回答を捏造しない。
4. 新規コードを出す前に、完成図の初稿と未決事項をユーザーへ提示する。
5. 完成図承認後、一つの実装依頼をテンプレートに沿って作る。

## 7. 直近の引継ぎ上の判断点

- 今後のFramework完成範囲と、その評価に使う最小ゲームを決める。

- 一括命名移行は別計画。コード出力前規約の遵守と全体移行完了は別。
