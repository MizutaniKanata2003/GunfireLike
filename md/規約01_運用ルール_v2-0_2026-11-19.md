# GunfireLike 運用ルール・レビュー（規約 1/3）

版: 2.0  
更新日: 2026-11-19 JST  
用途: AIのコード出力手順、検証、レビュー、文書管理を定める。整形・コメント・構造は「規約02_コーディング規約」、命名は「規約03_命名規則」を参照する。

## 文書構成

| 文書 | 内容 |
|---|---|
| 規約01_運用ルール（本書） | 優先順位、コード出力手順、レビューチェックシート、文書管理 |
| 規約02_コーディング規約 | 整形、include、波括弧、空白、空行、コメント、構造・責務、行数上限 |
| 規約03_命名規則 | 命名一覧、略語、bool、記述例、適用・移行方針 |

3文書は一組で使用する。矛盾する場合は、優先順位（第1章）に従う。

## 1. 使用方法・優先順位・今回の改訂

### 優先順位

1. ユーザーの最新の明示指示。
2. 本書の確定規則。
3. 現行コードと対象APIの契約、タスクで合意した設計。
4. 旧Markdownと過去の提案（参考情報）。

- コードの実装事実と、今後従う命名・整形規則を区別する。
- 既存コードの古い書式を理由に、確定規則を元へ戻さない。
- 未変更の既存API・外部API名を維持する必要がある場合、対象と理由を明記する。
- 本書の統合はリポジトリー全体への改名・整形適用済みや、ビルド成功を意味しない。

### 版1.1の変更

| 対象 | 現行規則 | 例 |
|---|---|---|
| namespace名 | 接頭辞なしのアッパースネークケース | SHOP_MESSAGE |
| namespace内の定数 | ns_ + アッパースネークケース | ns_DISPLAY_DURATION_SECONDS |
| クラスの定数メンバー | m_ + アッパースネークケース（変更なし） | m_MAX_HP |

ns_はnamespace名からnamespace内の定数名へ移動する。関数・型・通常変数へ一律に付ける規則ではない。
匿名namespace内の定数にも適用する。匿名namespace自体を命名のためだけに名前付きへ変更しない。

```cpp
// Shopの購入結果表示に使用する定数をまとめる。
namespace SHOP_MESSAGE
{
  //========= 表示時間定数=========
  // 購入結果を表示する標準時間。単位は秒。
  constexpr float ns_DISPLAY_DURATION_SECONDS = 1.5f;
}
```

参照例:

```cpp
m_remainingTime = SHOP_MESSAGE::ns_DISPLAY_DURATION_SECONDS;
```

## 2. AIのコード出力手順

### 作成前

1. 対象コミットまたは提示コードの版を特定する。
2. 対象Header、cpp、呼び出し元の本文を確認する。
3. 目的、変更対象、非対象、保持する挙動を整理する。
4. 必須情報が不足している場合は確認し、未読の実装を推測で補わない。
5. 基準版を対象ブランチのコミットSHAまたはユーザー指定の添付ファイルで特定する。リポジトリの状態は、同一コミットの実パス、`#include`、必要に応じて `.vcxproj` と `.filters` を照合して報告する。コミット名や検索結果だけで移動の成否を判定しない。
6. ユーザーが報告した工程の完了と、自分で取得・照合した範囲を区別する。完了済み工程を差し戻す場合は、基準コミット、対象パス、矛盾を示す参照または登録を明記する。取得失敗や新規作成予定ファイルの不在を、前工程の未完了の根拠にしない。
7. ツールの表示抜粋と入力ファイル本体を区別する。添付や別経路で全文を読める場合はその本文を使い、再添付は求めない。添付版とリポジトリ版に差がある場合は、差の箇所と採用する基準版を明記する。

### 出力直前

1. 整形・命名・コメントを本書へ照合する。
2. タブ混入、180文字制限、引数整列、空行、責務グループを確認する。
3. 宣言・定義・呼び出しと関連ファイルの整合を確認する。
4. チェックシートの該当項目を確認し、不適合を修正する。
5. 静的確認とビルド・実機検証を分け、未確認事項を記録する。
6. cpp内の各処理グループに目的の説明があり、読み取りにくい処理に理由・前提の補足があるか確認する。

7. 各条件分岐・繰り返しの先頭、標準・Windows Headerの各include、設定値、難読計算、個別失敗経路の説明を確認する。
8. コメントが実装を上回る安全性・復旧・設計意図を保証していないことと、コード例も追加規則に整合することを確認する。
9. 構造・責務の基準（コーディング規約の第13節：関数の長さ・ネスト・クラスの大きさ・引数の数・処理の流れ・同じ役割のメンバー変数・重複）に適合することを確認する。
10. 報告と確認根拠を突き合わせる。未取得・未実装・未出力・未検証を区別する。成果物が実際に生成されたことを確認してから「出力済み」と記載する。規約照合・差分適用検査・構文検査・MSVCビルド・実機確認は、実施したものだけを報告する。
11. 変更後の物理行数をコーディング規約の13.9項に照らして確認する。不適合の場合は修正し、再検査を通過するまで出力しない。

### 出力時

- 対象ファイルと追加・削除・置換位置を明記する。
- 全体置換と部分置換を区別し、適用可能な単位で出力する。
- 完成コードに省略記号や未定義の仮APIを混ぜない。説明例には説明用と明記する。
- 既存API名を維持した例外、未確認事項、適用後の確認手順を示す。
- 確認していないことを確認済みと報告しない。
- 必須の整合確認ができない場合、適用可能な完成コードとは表現しない。
- 出力前レビューの資料は、ユーザーが不要と指定した場合は出力しない。内部での照合は省略しない。

内部確認の記録形式例:

```text
対象・変更内容:
基準版:
静的確認:
- 整形・行幅・命名:
- 改行・グループ化・コメント:
- 処理グループの目的説明・難読箇所の理由説明:
- 各条件・繰り返し、include用途、設定値、局所計算、個別失敗経路の説明:
- 構造・責務の基準（関数・ネスト・クラス・引数・流れ・メンバー変数・重複）:
- 宣言・定義・呼び出し:
既存API名の維持・例外:
未確認事項:
ビルド・実機検証: 実施結果または未実施
適用後の確認項目:
```

全チェック項目を毎回答へ転載する必要はないが、実際に照合してからコードを提示する。

## 5. レビューチェックシート

### 1. レビュー対象と記録

| 項目 | 記入欄 |
|---|---|
| タスクID・目的 | |
| 基準コミットSHA | |
| レビュー対象コミット・差分 | |
| 対象ファイル | |
| レビュー担当・確認日 | |
| 変更してはいけない挙動 | |
| 既知の制限 | |

#### 記入方法

- 各項目は「適合／不適合／未確認／対象外」で管理する。
- チェック済みは「適合」を意味する。未確認や対象外を適合扱いにしない。
- 対象外には理由、未確認には確認方法を記録する。
- 不適合はファイル・行または識別子・問題・対応方針を記録する。
- 既存の規約差異と、今回追加した違反を区別する。
- 構造・安全性の項目はレビュー観点であり、未決の設計を自動的に確定するものではない。

### 2. 変更範囲・根拠

- [ ] 目的、変更対象、非対象が明確になっている。
- [ ] 基準版と差分が特定されている。
- [ ] 対象Header、cpp、呼び出し元の本文を確認している。
- [ ] 取得成功表示だけで本文を読了扱いにしていない。
- [ ] 原則として一つの責務または一つの不具合に限定している。
- [ ] 無関係な整形、一括改名、機能追加を混ぜていない。
- [ ] 未確認の旧資料やコミット名だけで実装状況を断定していない。
- [ ] 基準版・実パス・参照・登録の確認結果と、工程の状況報告が一致している。
- [ ] 成果物の生成と、実施済みの検証・未実施の検証を区別して記録している。

### 3. 整形・行幅

- [ ] インデントはスペース2個で、タブ文字がない。
- [ ] インデント・引数整列用空白を含めて、各行が180文字以内である。
- [ ] 短い宣言、呼び出し、初期化を不要に分割していない。
- [ ] 長い引数列は意味・役割のグループ境界で改行している。
- [ ] 引数の継続行は最初の引数位置にそろえている。
- [ ] 分割した引数グループも180文字以内である。
- [ ] 一引数一行へ機械的に展開していない。
- [ ] 関数、型、namespaceの開始波括弧が次行にある。
- [ ] 制御ブロック、Lambdaの開始波括弧が同じ行にあり、直前に空白がない。
- [ ] elseは次行、catchは直前の閉じ波括弧と同じ行にある。
- [ ] doに続くwhileが次行にある。
- [ ] 関数名・制御キーワードと開き括弧の間に空白がない。
- [ ] 括弧内、初期化リスト内、カンマ前後の空白が設定に合っている。
- [ ] 代入演算子・三項演算子の周囲に空白がある。
- [ ] アクセス指定子、case、プリプロセッサなどの配置が確定設定に合っている。
- [ ] HLSLは幅2を使い、C++固有の書式を無条件に適用していない。

### 4. include・宣言・定義

- [ ] includeは「対応Header（cppのみ）→Windows→C++標準→外部ライブラリ→Debug→Framework→Scene」の順である。
- [ ] 使用するincludeグループの先頭に名前のコメントがある。
- [ ] 標準・Windows Headerはグループ名だけでなく、各includeにも具体的用途の説明がある。
- [ ] 未使用グループの見出しを残していない。
- [ ] includeグループ間を空行1行で区切っている。
- [ ] 必要な標準Headerなどを、偶然の間接includeに依存せず確認している。
- [ ] Headerの宣言とcppの定義の型、引数、constなどが一致している。
- [ ] cppの定義順がHeaderの宣言順に対応している。
- [ ] Header内定義とcpp定義が重複していない。
- [ ] 追加・削除したソース、Header、Shaderのプロジェクト登録を確認している。

### 5. 命名

- [ ] クラス名、関数・メソッド名はアッパーキャメルケースである。
- [ ] 構造体名、列挙型名はアッパースネークケースである。
- [ ] クラスの通常メンバーはm_ + ローワーキャメルケースである。
- [ ] ローカル変数はスネークケースである。
- [ ] 通常の関数引数はローワーキャメルケースである。
- [ ] 構造体の通常フィールドは接頭辞なしのローワーキャメルケースである。
- [ ] 列挙子はe_ + アッパースネークケースである。
- [ ] 名前付きnamespaceは接頭辞なしのアッパースネークケースである。
- [ ] 名前付き・匿名namespace内の定数はns_ + アッパースネークケースである。
- [ ] クラスの定数メンバーはnamespace内でもm_ + アッパースネークケースを維持している。
- [ ] 型エイリアスはアッパーキャメルケースである。
- [ ] 型を受け取るテンプレート仮引数はT + アッパーキャメルケースである。
- [ ] 数値などを受け取るテンプレート仮引数はアッパースネークケースである。
- [ ] ファイル名の本体部分はアッパーキャメルケースである。
- [ ] 通常の名前付き定数はアッパースネークケースである。
- [ ] 定数メンバーはm_ + アッパースネークケースである。
- [ ] constの計算結果ローカルを、理由なく定数名形式に変えていない。
- [ ] HP、UI、GPU、FPSなどの略語を大文字で維持している。
- [ ] boolはis / has / can / should / didなどで意味が分かる。
- [ ] 外部APIの識別子を本プロジェクト規則へ合わせて改名していない。
- [ ] 改名した識別子の参照先と関連ファイルを確認している。

### 6. 空行・グループ化

- [ ] 同じ目的の連続処理を空行で分断していない。
- [ ] 値の取得と直後の単純な検証を原則として一組にしている。
- [ ] 異なる責務のグループ間に空行1行を入れている。
- [ ] グループコメントの直後に空行を入れていない。
- [ ] 関数定義間とHeaderのグループ間は空行1行である。
- [ ] 原則として関数内に連続した空行を2行以上入れていない。
- [ ] return直前に機械的な空行を挿入していない。
- [ ] 初期化・判定・副作用・返却を分類だけで細切れにせず、一つの目的・処理経路を保っている。
- [ ] 同じ役割のメソッド、メンバー、定数をグループ化している。
- [ ] 各グループの先頭にグループ名のコメントがある。
- [ ] cpp内の空行で区切る各処理グループに、担当内容・目的の説明がある。
- [ ] 空行を作るためだけに補助関数を増やしていない。

### 7. コメント・契約

- [ ] 各if・else if・elseに、条件と実行・省略・終了内容の説明がある（一行returnを含む）。
- [ ] switchとcase・default、および各for・while・do-whileに、分類・範囲・継続終了条件・目的の説明がある。
- [ ] 複合条件の短絡評価がnull参照や除算の回避に関係する場合、その依存関係を説明している。
- [ ] C++標準・Windows Headerの各includeに、使用する関数・型・マクロと対象ファイル内の具体的用途がある。
- [ ] 初期値・定数・設定値に、各成分の意味・単位・座標系と必要な影響範囲の説明がある。
- [ ] 数値の意味と採用理由を区別し、未確認の理由や単位を作っていない。
- [ ] 難しい計算・代入・変換には、概要だけでなく対象箇所にも入力・変換・用途の説明がある。
- [ ] 各Resource生成・読込失敗判定に、失敗対象・解放範囲・残る状態・戻り方の説明がある。
- [ ] 検出失敗と例外を区別し、未実装の捕捉・復旧・巻き戻しを保証していない。
- [ ] 必須の局所コメントを省略せず、説明用のコード例にも追加規則を適用している。
- [ ] Header先頭に、扱うクラス・型の役割を記述している。
- [ ] メソッドの役割を記述している。
- [ ] 各引数に対して一つずつ説明がある。
- [ ] メンバー変数の保持内容と用途を記述している。
- [ ] namespaceと定数グループの用途を記述している。
- [ ] enum / struct自体の役割を記述している。
- [ ] 各列挙子と各フィールドの意味を記述している。
- [ ] 長いstructは関連フィールドをグループ化している。
- [ ] 必要な単位、範囲、null可否、呼び出し前提が分かる。
- [ ] 必要な所有・非所有、寿命、副作用、戻り値の意味が分かる。
- [ ] 特殊な処理順や計算には、必要な理由の説明がある。
- [ ] 可読性の低い条件式・ビット演算・座標変換・Resource処理に、目的や前提を補っている。
- [ ] 失敗時の巻き戻し・解放順・状態フラグ変更の理由を必要に応じて説明している。
- [ ] コメントのためだけに処理を細分化したり、コードの読み上げを繰り返したりしていない。
- [ ] Headerとcppに同じ長文説明を重複していない。
