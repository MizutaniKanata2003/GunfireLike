## 2. AIのコード出力手順

### 作成前

1. 対象コミットまたは提示コードの版を特定する。
2. 対象Header、cpp、呼び出し元の本文を確認する。
3. 目的、変更対象、非対象、保持する挙動を整理する。
4. 必須情報が不足している場合は確認し、未読の実装を推測で補わない。

### 出力直前

1. 整形・命名・コメントを本書へ照合する。
2. タブ混入、180文字制限、引数整列、空行、責務グループを確認する。
3. 宣言・定義・呼び出しと関連ファイルの整合を確認する。
4. チェックシートの該当項目を確認し、不適合を修正する。
5. 静的確認とビルド・実機検証を分け、未確認事項を記録する。
6. cpp内の各処理グループに目的の説明があり、読み取りにくい処理に理由・前提の補足があるか確認する。

7. 各条件分岐・繰り返しの先頭、標準・Windows Headerの各include、設定値、難読計算、個別失敗経路の説明を確認する。
8. コメントが実装を上回る安全性・復旧・設計意図を保証していないことと、コード例も追加規則に整合することを確認する。

### 出力時

- 対象ファイルと追加・削除・置換位置を明記する。
- 全体置換と部分置換を区別し、適用可能な単位で出力する。
- 完成コードに省略記号や未定義の仮APIを混ぜない。説明例には説明用と明記する。
- 既存API名を維持した例外、未確認事項、適用後の確認手順を示す。
- 確認していないことを確認済みと報告しない。
- 必須の整合確認ができない場合、適用可能な完成コードとは表現しない。
- 出力前レビューの資料は、ユーザーが不要と指定した場合は出力しない。内部での照合は省略しない。

内部確認の記録形式例:

```text
対象・変更内容:
基準版:
静的確認:
- 整形・行幅・命名:
- 改行・グループ化・コメント:
- 処理グループの目的説明・難読箇所の理由説明:
- 各条件・繰り返し、include用途、設定値、局所計算、個別失敗経路の説明:
- 宣言・定義・呼び出し:
既存API名の維持・例外:
未確認事項:
ビルド・実機検証: 実施結果または未実施
適用後の確認項目:
```

全チェック項目を毎回答へ転載する必要はないが、実際に照合してからコードを提示する。

## 3. 整形・構成・コメント

### 1. 本書の位置付け

- 本書は、Visual Studio設定と本会話で確定した方針をまとめる。
- 最新コードに書式の差異が残っていても、それを本書の変更根拠にはしない。
- 現状確認中に、整形変更とロジック変更を混ぜない。
- 未変更の全ファイルへ適用済みであることや、ビルド・動作検証済みであることを意味しない。

### 2. インデント・行幅

- インデントはスペース2個。タブ文字は使用しない。
- 1行は先頭のインデントと引数整列用の空白を含めて180文字以内とする。
- 短い宣言・呼び出し・初期化を不必要に分割しない。
- HLSLもインデント幅2とする。C++固有の波括弧・空白規則は自動的にHLSLへ適用しない。

### 3. include順

1. cpp自身に対応するHeader（cppのみ）
2. Windows
3. C++標準ライブラリ
4. 外部ライブラリ（DirectX・DirectXTK・Dear ImGuiなど）
5. Debug
6. Framework
7. Scene

- Headerでは1を省略する。
- 使用しないグループは見出しごと省略する。
- 各グループの先頭にグループ名のコメントを置く。
- グループ間は空行1行で区切る。
- 同一グループ内のアルファベット順などは、本会話では未指定。
- C++標準ライブラリ・Windows関連Headerの各includeには、そのファイルで使用する関数・型・マクロと利用目的を、行末または直前に書く。
- グループ名だけでは各Headerの用途説明を代用しない。詳細は第3章9節「C++標準ライブラリ・Windows Headerの用途」に従う。

説明用の構成例（include用途は例であり、現行ShopSceneの依存を保証しない）:

```cpp
#include "../H/ShopScene.h"

//========= C++標準ライブラリ インクルード=========
#include <algorithm> // std::clampによる値の範囲制限に使用する。
#include <array> // 要素数が固定されたデータをstd::arrayで保持する。

//========= 外部ライブラリ インクルード=========
#include <DirectXMath.h>

//========= Framework インクルード=========
#include "Framework/Audio/H/AudioSystem.h"

//========= Scene インクルード=========
#include "Scene/Common/H/SceneManager.h"
```

### 4. C++の波括弧と改行

- 関数、class、struct、namespaceの開始波括弧は次行。
- if、for、while、switchなどの制御ブロックの開始波括弧は同じ行。
- Lambdaの開始波括弧は同じ行。
- ブロック開始波括弧の直前に空白を入れない。
- elseは次行。catchは直前の閉じ波括弧と同じ行。
- doに続くwhileは次行。
- 空の関数・型の開閉波括弧は同じ行にする設定を用いる。
- 既存の一行スコープを保持する設定を用いる。新しい処理を一行へ無理に圧縮しない。

説明用の例:

```cpp
void Example::Update(float deltaTime)
{
  // 時間が進まない更新ではアニメーション状態を変更しない。
  if(deltaTime <= 0.0f)return;

  // 有効な対象だけアニメーションを進め、無効な対象は初期状態へ戻す。
  if(m_isActive){
    UpdateAnimation(deltaTime);
  }
  // 無効な対象はアニメーションを初期状態へ戻す。
  else{
    ResetAnimation();
  }
}
```

### 5. C++の空白

- 関数名と開き括弧の間に空白を入れない。
- 制御キーワードと開き括弧の間に空白を入れない。
- 関数・条件式・式・キャストの括弧内に空白を入れない。
- カンマの前後に空白を入れない。
- 初期化リストの開始波括弧の直前と内側に空白を入れない。
- 空の括弧・波括弧・角括弧の内側に空白を入れない。
- 代入演算子と三項演算子の周囲には空白を入れる。
- セミコロン直前の空白を除去し、直後には必要な空白を入れる。
- コンストラクター初期化リストおよび継承のコロン直前に空白を入れない設定を用いる。

```cpp
const bool is_aimed = target == m_aimedTarget;
const float scale = is_aimed ? aimed_scale : normal_scale;
DirectX::XMFLOAT3 position{0.0f,1.0f,7.0f};

DrawObject(position,color);
```

### 6. 長い呼び出し・引数列

- 180文字を超える場合、意味・役割のグループ境界で改行する。
- 継続行は最初の引数の開始位置にそろえる。
- 一引数一行へ機械的に展開しない。
- 分割後も180文字を超える場合は、グループ内を追加で分割する。
- グループの意味はメソッド宣言・引数コメント・呼び出し元から判断する。

```cpp
m_enemyController.Initialize(stage_data.enemyMaxHP,ENEMY_NORMAL_ATTACK_INTERVAL,ENEMY_NORMAL_ATTACK_RANGE_SQUARED,
                             stage_data.enemyDamage,stage_data.specialAttackInterval,special_attack_range_squared,stage_data.enemyDamage * ENEMY_SPECIAL_ATTACK_DAMAGE_MULTIPLIER);
```

### 7. 空行と処理グループ

- 同じ目的の連続処理は、空行なしでまとめる。
- 値の取得と直後の単純な検証は、原則として一組にする。
- 異なる責務のグループ間には空行1行を入れる。
- グループコメントの直後に空行を入れない。
- 関数定義間、Header内の異なるグループ間は空行1行。
- 関数内で空行を2行以上続ける運用は原則としてしない。
- return直前を機械的に空けない。直前の処理との関係で判断する。
- 初期化・判定・副作用・結果返却という分類だけで処理を細切れにしない。
- 一つの目的や成功・失敗などの処理経路を優先してまとめる。
- 空行を作るためだけに補助関数を増やさない。
- 主にcpp内では、空行で区切る各処理グループの先頭に、何を担当するグループか説明するコメントを書く。
- 「処理」「設定」だけの見出しにせず、対象と目的が分かる説明にする。
- 説明を追加するために、同じ責務の処理を新しく分断しない。

説明用の例:

```cpp
// 購入対象を取得し、操作可能な対象か確認する。
const SHOP_UPGRADE_DATA* upgrade_data = FindUpgradeData(target);
// 対象が見つからなければ、購入処理や表示状態の変更を行わず戻る。
if(upgrade_data == nullptr)return;

// 購入を試行する。
const bool is_purchase_successful = progress.TryPurchaseUpgrade(upgrade_data->upgradeType);

// 購入結果と、その表示時間を設定する。
m_purchaseResult = is_purchase_successful ? PURCHASE_RESULT::e_SUCCESS : PURCHASE_RESULT::e_FAILURE;
m_interactionMessageTimer = SHOP_MESSAGE::ns_DISPLAY_DURATION_SECONDS;
```

### 8. Headerとcppの構成

- 同じ役割のメソッドやメンバー変数をグループ化する。
- グループ先頭にグループ名のコメントを書く。
- cppで定義するメソッドは、Headerの宣言順に合わせる。
- Header内で定義済みのメソッドをcppで重複定義しない。
- include順とメソッドの宣言・定義順は、別の規則として扱う。

### 9. コメント

#### Header先頭

- どのようなクラス・型を扱うファイルか、その責務を記述する。

#### メソッド・引数

- メソッドが何を担当するか記述する。
- 各引数について、何を受け取るかを一つずつコメントする。
- 必要に応じて単位、範囲、null可否、事前条件を記述する。
- 戻り値の意味、失敗や対象なしの表現が分かりにくければ補足する。

#### メンバー変数

- 何を保持し、何に使う値か記述する。
- 必要に応じて単位、所有・非所有、寿命の前提を記述する。

#### namespace・定数

- namespaceに何をまとめるか説明する。
- 定数群を用途ごとにグループ化し、先頭に名前と役割を書く。
- namespace全般の説明を「定数」に限定せず、中に置く内容に合わせる。

#### enum・struct

- 型自体の役割を書く。
- 各列挙子と各フィールドの意味を書く。
- フィールドが多い場合は関連するものをグループ化し、グループ名を書く。

#### 理由・制約・副作用

- 単位、所有権、制約、副作用、戻り値、特殊な処理順の理由を必要な箇所に補足する。
- Headerでは利用者向けの契約、cppでは実装理由や注意点を中心にする。
- 同じ長文説明をHeaderとcppへ重複記述しない。
- 実装の動作を読み上げるだけの冗長コメントは避ける。

#### cpp内の処理グループと可読性が低い処理（版1.2追加）

- 空行で区切る処理グループには、グループの目的・担当内容を説明するコメントを先頭に付ける。
- グループコメントと対象処理の間に空行を挟まない。
- 特に、複雑な条件式・ビット演算・座標変換・サイズ計算・Resourceの生成解放・失敗時の巻き戻しには、読み取りに必要な説明を補う。
- 処理順に意味がある場合は、その順序である理由や、順序変更で崩れる前提を説明する。
- フラグ変更では、以後に許可・抑止する処理が分かるようにする。
- 失敗経路では、解放する対象・解放しない対象・出力先に残る状態を必要に応じて説明する。
- 説明は実装事実に基づき、未実装の安全策や未確認の意図を実装済みとして記述しない。
- 毎行コメントする規則ではない。ただし各条件・繰り返しの先頭コメントは必須とし、局所説明を要する計算も概要だけで済ませない。目的を共有するその他の処理は一つの説明でまとめる。
- 短い自明な処理に同じ内容を繰り返さず、可読性が悪い箇所を優先して詳しく説明する。
- コメント補完と、機能追加・不具合修正・処理順変更を混ぜない。

説明用の例（実装への追加指示ではない）:

```cpp
// 描画側の初期化失敗では、先に成功したWin32側とContextを逆順に終了する。
// 完了フラグはまだfalseのため、通常のUninitではなくこの経路で巻き戻す。
if(!ImGui_ImplDX11_Init(graphics.GetDevice(),graphics.GetContext())){
  ImGui_ImplWin32_Shutdown();
  ImGui::DestroyContext();
  return false;
}

// 両バックエンドの成功後にだけ、フレーム処理と通常終了を許可する。
m_isInitialized = true;
return true;
```

```cpp
//========= 更新関数=========
// 表示時間を更新し、終了した購入結果を非表示にする。
// deltaTime: この更新で進める経過時間。単位は秒。
void Update(float deltaTime);

//========= 購入結果表示状態=========
// 現在HUDへ表示する購入結果。
PURCHASE_RESULT m_result{PURCHASE_RESULT::e_NONE};
// 購入結果を表示する残り時間。単位は秒。
float m_remainingTime{};
```

#### 条件分岐・繰り返しの先頭コメント（2026-11-14追加）

- 自作コードの各条件分岐・繰り返しの先頭にコメントを記載する。Header内の実装および自作HLSLに該当する構文にも適用する。
- if・else ifは条件判定の直前に、何を判定し、どの場合にどの処理を実行・省略・終了するかを書く。一行の早期returnも対象とする。
- elseは直前に、先行条件が成立しない場合に扱う状態と処理を書く。elseの既存配置規則は変更しない。
- switchは分岐対象と分類の目的を先頭で説明し、各case・defaultの扱いも説明する。複数ラベルが同じ処理を共有する場合は、その対応をまとめて説明できる。
- for・while・do-whileは対象、走査範囲・方向、継続・終了条件、目的を説明する。do-whileでは先頭に全体の説明を置き、末尾条件が読み取りにくい場合は近くにも補足する。
- 複合条件は何をまとめて確認するかを書く。短絡評価の順序がnull参照や除算の回避に関係する場合は、その依存関係も説明する。
- 処理グループの概要だけで個別条件の説明を済ませない。直前の既存コメントが条件と処理を十分説明する場合は、同じ説明を二重に追加せず補完する。
- 条件式の記号を読み上げるだけの「0より大きい場合」ではなく、「長さが正の場合だけ単位化し、0除算を避ける」のように処理との関係を書く。
- 説明に必要な空白や改行は整形規則に従う。条件の評価順、比較、短絡、分岐、return位置をコメント追加の都合で変更しない。

説明用の例（既存実装への機能追加指示ではない）:

```cpp
// 視線を水平面へ投影し、正規化に必要な水平距離を求める。
XMFLOAT3 forward = camera.GetForward(); // カメラの前方向を取得する。
forward.y = 0.0f; // 上下成分を除き、移動方向をX・Z平面へ限定する。
const float forward_length = std::sqrt(forward.x * forward.x + forward.z * forward.z); // 水平成分の長さを求める。
// 水平距離が正の場合だけ単位化し、長さ0のベクトルでは除算しない。
if(forward_length > 0.0f){
  forward.x /= forward_length; // 水平方向を保ちながらX成分を単位長へ揃える。
  forward.z /= forward_length; // 同じ長さでZ成分も割り、水平ベクトル全体を単位化する。
}
```

#### C++標準ライブラリ・Windows Headerの用途（2026-11-14追加）

- 各includeの行末または直前に、そのファイルで使用する代表的な関数・型・マクロと具体的な用途を書く。
- 「標準機能用」「Windows機能用」「数学用」だけで済ませない。複数用途がある場合は主要なものをまとめて説明する。
- Headerでもcppでも、そのファイルの本文での用途を確認して書く。間接includeによる未確認の用途は断定しない。
- 未使用が疑われるHeaderに架空の用途を付けない。不要includeの削除は影響を確認してから行い、コメント補完に無断で混ぜない。
- 既存のincludeグループ名、順序、空行は維持する。説明込みで180文字を超える場合は直前コメントに分ける。

#### 初期値・定数・設定値の意味と採用理由（2026-11-14追加）

- 初期値・定数・設定値は、表す内容、用途、必要な単位・座標系・範囲を説明する。複数成分を持つ値は各成分の意味も示す。
- 設定を変更したときに影響する動作、関連する閾値・範囲・転送配置・他ファイルとの対応を、必要な箇所で補足する。
- 実装上の意味と、その数値を採用した設計理由は区別する。理由を確認できた場合は書き、確認できない場合は数値の意味と既存設定を維持する事実を書く。
- 例えば初期位置(0.0,1.6,-5.0)では各軸の開始座標と範囲補正との関係を説明する。速度6.0は、正規化した入力方向へ掛ける毎秒6.0ワールド距離単位の設定として説明する。
- ワールド距離を根拠なくメートルと呼ばない。「1.6は人の目の高さ」「6.0は操作しやすい速度」など、未確認の採用理由は作らない。
- グループ単位の共通説明と値ごとの説明を組み合わせ、単なる「初期値」「速度」という名称の繰り返しにしない。

#### 計算・代入・データ変換の局所説明（2026-11-14追加）

- 処理グループの概要に加え、読み取りにくい計算・代入・変換には対象行の直前または行末に説明を付ける。
- 入力、計算や変換の目的、出力の用途、必要な前提、単位を示す。複数行をまとめる場合も各行の意味が追える説明にする。

- ビット演算では取り出すbit数、シフト量、マスク、変換表の対応を書く。元の式や演算順を説明の都合で変更しない。
- 毎行コメントを機械的に要求するものではない。ただしa.txtで指摘されたような、個々の行の意味を読む必要がある箇所は概要だけで済ませない。

#### 低レベル基盤コードの詳細コメント規則（2026-11-13追加確定）

##### 1. 適用対象

レンダリング、Shader、Texture、Buffer、音声など、デバイス関連のAPIやライブラリを使用して、Resourceの生成・変換・転送・状態設定・実行・解放を行う基盤コードに適用する。

直接APIを呼び出す箇所だけでなく、その前後で必要となるデータ変換、ファイル解析、所有管理、初期化失敗時の後始末も対象とする。

本プロジェクトでは、GraphicsSystem、各Renderer、TextureLoader、ConstantBuffer、AudioSystem、HLSL、および関連する転送データ構造などが該当する。

##### 2. 基本原則

これらのコードでは、通常のゲームロジックよりも詳しくコメントを記載する。

API名や設定値を読むだけでは分かりにくい、次の内容を説明する。

- 何のための処理か。
- 設定値や引数が何を意味するか。
- 前後の処理や、他のファイルとどのように対応するか。
- なぜその順序で処理する必要があるか。
- 何を所有・変更・解放するか。
- 失敗した場合に、何が残り、呼出側に何が求められるか。

コメントを読めば、関連APIに不慣れな開発者でも、処理の流れと変更時に守るべき条件を追える状態を目指す。

##### 3. 必ず説明する観点

| 観点 | 記載する内容 |
|---|---|
| 責務 | このファイル・型・メソッドが担当することと、担当しないこと |
| 処理グループ | 空行で区切った処理群の目的、入力、処理結果 |
| API・設定値 | 重要な引数・Flag・Format・Usageなどの意味と、この処理での用途 |
| データの対応 | CPUとGPU、頂点構造体とShader入力、音声データと再生Instanceなどの関係 |
| 単位・座標系 | バイト数、要素数、pixel、秒、ラジアン、Local／World／View／Clipなど |
| 所有と寿命 | 所有者、借用参照、依存先、参照が無効になる条件 |
| 処理順 | 生成・更新・Bind・実行・解放の順序と、その順序を守る理由 |
| 副作用 | 変更する描画状態・再生状態・出力先と、元の状態へ戻すかどうか |
| 失敗時 | 判定方法、部分生成済みResource、後始末、戻り値・例外、再試行や復旧の有無 |
| 制限 | 未対応形式、未検証の条件、呼出側で満たす必要がある前提 |

##### 4. コメントの配置

- ファイル先頭では、全体の責務と依存関係を説明する。
- Headerでは、利用者が守る契約、引数、戻り値、所有関係、寿命、呼出条件を説明する。
- cppでは、実装の仕組み、設定の意味、処理順の理由、失敗経路を説明する。
- 処理グループの先頭には、そのグループの目的を書く。
- 重要な設定値・複雑な計算・分かりにくいAPI呼出には、その近くにも補足を書く。
- 他ファイルとの対応が重要な箇所では、対応する型名、Shader名、slot、semanticなどを具体的に示す。

##### 5. 詳細さの判断基準

次のいずれかに該当する箇所は、概要コメントだけで済ませず、理由や前提まで補足する。

- 設定値を変更すると、表示・再生・転送結果が変わる。
- 処理順を入れ替えると、正常に動かなくなる。
- 別ファイルとの対応を崩すと、不具合が発生する。
- 失敗後のResourceや状態が、その後の処理へ影響する。
- 所有権や寿命を誤ると、不正参照や解放漏れにつながる。
- コードだけでは、単位・座標系・データ形式・副作用が判断しにくい。

##### 6. 避けること

- API名や代入文を日本語へ置き換えただけのコメント。
- 毎行へ同じ程度の説明を付け、重要な注意点が埋もれる書き方。
- コメントのためだけに、同じ目的の処理を細分化すること。
- Headerとcppに同じ長文を重複させること。
- 未実装の安全策や復旧処理を、実装済みとして説明すること。
- 根拠のない設計理由を推測で記載すること。

設定を選んだ理由が確認できない場合は、設定の意味と現在の用途を説明し、「既存設定を維持している」と記載する。「高速化のため」「安全のため」などの理由を推測で断定しない。

##### 短い指示文

レンダリング・Texture・音声など、低レベルAPIを扱う基盤コードには、通常より詳しいコメントを記載する。処理の概要だけでなく、設定値の意味、データの対応、所有と寿命、処理順の理由、副作用、失敗時の状態まで説明する。特に、変更すると他の処理やファイルとの整合が崩れる箇所は、その依存関係と守るべき条件を明記する。

### 10. その他のインデント設定

- namespace内部はインデントする。
- public / privateなどのアクセス指定子を追加インデントしない。
- caseラベル、case内部、caseの波括弧を追加インデントしない設定を用いる。
- 波括弧自体は追加インデントしない。
- プリプロセッサはインデントしない。
- 長い引数の整列では2スペースの倍数よりも、最初の引数位置への整列を優先する。

## 4. 命名規則

### 1. 基本表記

- アッパーキャメルケース: 単語の先頭を大文字にして連結する。例: SceneManager
- ローワーキャメルケース: 最初の単語を小文字で始め、後続単語の先頭を大文字にする。例: deltaTime
- アッパースネークケース: 単語を大文字で記述し、アンダースコアで区切る。例: PURCHASE_RESULT
- スネークケース: 原則として小文字の単語をアンダースコアで区切る。例: remaining_time
- 略語については第3節の大文字維持規則を優先する。

### 2. 命名一覧

| 対象 | 規則 | 例 |
|---|---|---|
| クラス名 | アッパーキャメルケース | SceneManager |
| 関数・メソッド名 | アッパーキャメルケース | GetCurrentHP |
| 構造体名 | アッパースネークケース | SHOP_UPGRADE_DATA |
| 列挙型名 | アッパースネークケース | PURCHASE_RESULT |
| クラスのメンバー変数 | m_ + ローワーキャメルケース | m_currentHP |
| ローカル変数 | スネークケース | current_HP |
| 通常の関数引数 | ローワーキャメルケース | deltaTime、maxHP |
| 列挙子 | e_ + アッパースネークケース | e_MAX_HP_UPGRADE |
| 構造体のフィールド | ローワーキャメルケース | currentHP |
| 名前付きnamespace | アッパースネークケース（接頭辞なし） | SHOP_MESSAGE |
| namespace内の定数 | ns_ + アッパースネークケース | ns_DISPLAY_DURATION_SECONDS |
| 型エイリアス | アッパーキャメルケース | SceneOwner |
| 型を受け取るテンプレート仮引数 | T + アッパーキャメルケース | TValue、TScene |
| 数値などを受け取るテンプレート仮引数 | アッパースネークケース | ELEMENT_COUNT |

| 通常の名前付き定数 | アッパースネークケース | MAX_STAGE_COUNT |
| 定数メンバー | m_ + アッパースネークケース | m_MAX_HP |

#### 適用区分

- 通常のクラスメンバーにはm_を付ける。
- 通常の構造体フィールドにはm_を付けない。
- 定数メンバーには、通常のメンバー変数・フィールドとは別に定数メンバー規則を適用する。
- 型名とファイル名は別の規則である。構造体SHOP_UPGRADE_DATAのファイル名はShopUpgradeData.hとなる。
- 名前付き・匿名namespace内の定数にはns_を付ける。namespace名自体にはns_を付けない。
- ns_はnamespace内の定数に対する規則であり、内部の関数・型・通常変数すべてへ付ける指示ではない。
- クラス内の定数メンバーは、クラスがnamespace内にある場合もm_ + アッパースネークケースを維持する。
- constであることだけで、用途が通常のローカル変数から定数定義へ変わるわけではない。計算・取得結果を保持するconstローカルはローカル変数規則に従う。

### 3. 略語

略語は通常の大文字・小文字規則より優先し、すべて大文字にする。

例: HP、UI、GPU、FPS

| 対象 | 例 |
|---|---|
| メソッド | GetCurrentHP |
| クラスメンバー | m_currentHP |
| ローカル変数 | current_HP |
| 関数引数 | maxHP |
| 構造体フィールド | currentHP |
| 定数メンバー | m_MAX_HP |
| ファイル | GameUI.h |

略語から始まる場合も大文字を維持する。例: m_UIRenderer、UI_state、UIRenderer.h。

### 4. bool

boolは対象ごとの表記規則に加え、意味に応じてis、has、can、should、didなどを使う。

| 意味 | 例 |
|---|---|
| 現在の状態 | isActive |
| 所有・存在・実行済み | hasTarget |
| 実行可能 | canInteract |
